### 1.2 计费口径（决定一切的一条）

上游 `billing/balance` 的 `used_units` **等于**：

```
input_tokens + cache_read_input_tokens + output_tokens
```

实证：执落 `used=4,481,688` = `646,194 + 3,790,016 + 45,478`，逐位相等；
隐形守护者2 `used=519,949` = `14,926 + 500,352 + 4,671`，同样逐位相等。

**结论：缓存命中不是免费的，命中多少就计多少。** 这直接决定了放大层的打法——
不是“多生成”，而是“**多读大前缀**”。

## 2. 核心判断：为什么必须是双引擎

### 2.1 真活层的上限

单会话的 token 消耗 = 每回合上下文 × 回合频率。

- 本会话实测：约 2 次请求/分钟，每次 100–140K units → **13–20M/h**；
- 历史峰值：2026-11-01 23:00 一小时 613 请求 × 185K ≈ **113M/h**，但那是**多会话叠加**；
- 5 路会话全开、每路 13–20M/h → **65–100M/h**；
- 7.83h × 100M/h = **0.78B**，只能覆盖 53%，且要求 5 路全程不卡、不断、不排队。

所以：**只靠“认真干活”烧不完 14.66 亿**，这是算术问题，不是执行力问题。

### 2.2 放大层的上限

13.5 万 token 前缀命中缓存后，单请求 1.6–11s，单账号 5 路并发实测 210–292M/h。
按 250M/h 算，5–6h 烧完 1.47B；按 300M/h 算，4.9h。

放大层不产生“业务价值”，但它把**临期额度的残值**变成已用量，避免 09:00 直接归零。
它是兜底，不是主菜；主菜仍然是完美世界2.4 的 P0 第二轮。

### 2.3 双引擎的分工

| 层 | 消耗占比（目标） | 产出 | 运行方式 |
|---|---:|---|---|
| 真活层 | 20–35% | 完美世界2.4 P0/P1 代码、验收报告、知识库 | 主炉 1 路 + 旁路 4 路 |
| 放大层 | 65–80% | 无（保底烧完） | 5–10 车道钉号并发 |
| 合计 | 100% | 额度清零 + 真实交付 | 并行，互不阻塞 |

## 6. 烧速模型与调度算法

### 6.1 总速率

```
R_total = R_work + R_amp

R_work ≈ N_sessions × 13~20M/h        （会话遥测实测）
R_amp  ≈ N_lanes × 135K × 3600 / T    （T = 单请求耗时，1.6~11s）
```

实测标定：

| N_lanes | T | R_amp |
|---:|---:|---:|
| 1 | 1.6–3.6s | 149M/h |
| 5（同账号） | 1.7–11.4s | 210–292M/h |
| 5（分账号，目标） | 2–8s | 250–350M/h |
| 10（分账号，试探） | 2–12s | 400–600M/h（需验证 429/3009） |

### 6.2 剩余量与 ETA

```
remaining = Σ accounts.quota["GLM-5.3-Flash"].remaining
eta_hours = remaining / R_total
```

当前 1.466B 的 ETA：

| 综合速率 | 烧完耗时 | 预计见底 | 缓冲 |
|---:|---:|---|---:|
| 150M/h | 9.78h | 10:56 | **来不及** |
| 200M/h | 7.33h | 08:30 | 0.5h |
| 250M/h | 5.87h | 07:02 | 2.0h |
| 300M/h | 4.89h | 06:03 | 3.0h |
| 400M/h | 3.67h | 04:50 | 4.2h |

**目标带：250–350M/h。** 低于 200M/h 触发加车道；高于 350M/h 且出现 429/3009 则降车道。

### 6.3 车道调度规则

1. **一账号一主车道**：5 个账号 → 5 条钉号车道，保证每个账号都动。
2. **加车道**：若 10 分钟平均 < 220M/h，且 429/3009 < 1%，追加 1 条（最多 10 条，
   即每账号 2 条）；新车道随机挑剩余最多的账号。
3. **减车道**：若 429/3009 > 5% 或 3012 出现 ≥2 次，砍掉一半车道，冷却 5 分钟。
4. **账号耗尽**：响应含 `1005` / `exceed quota` → 该账号移出车道池，车道改钉剩余最多账号。
5. **前缀刷新**：每条车道固定 400K chars 前缀；缓存 TTL 约 5 分钟，车道空闲超过 4 分钟
   自动重发一次预热请求。
6. **尾问随机化**：大前缀后追加一句随机“总结/风险/端点”问题，避免完全相同的请求体，
   同时不破坏前缀缓存。

## 7. 风控与止损（红线）

### 7.1 上游信号与处置

| 信号 | 含义 | 处置 |
|---|---|---|
| `3012` / `405 unusual activity` | 请求形状/风控命中 | **立即全停 10 分钟**；检查是否误带 `system` 块；恢复后只用 CLI 形态 |
| `429` 普通频控 | 请求太快 | 该车道退避 `Retry-After`，全局降 50% 车道 |
| `429 code 3009` | 模型并发租约未释放 | 短等 1s × 3 轮；不换模型、不换号；仍失败则该车道减 1 |
| `1005` / `exceed quota limit` | 账号额度耗尽 | 账号移出池，车道改钉其他账号 |
| `502/503` | 上游故障 | 账号冷却 300s；全局降到 2 车道观察 |
| `risk_strikes ≥ 2` | 逼近禁用阈值 | 该账号停 30 分钟；只保留 1 条探测车道 |

### 7.2 账号级保险

- 每个账号一个 `x-zcode-account` 钉号，**不做跨号轮询**（轮询会打散前缀缓存，也会让
  单个账号的异常更难定位）；
- 每个账号独立统计成功/失败/3012/429；单账号连续 3 次失败 → 该车道退避 60s；
- 任何账号 `status` 变为 `invalid` / `disabled` → 立即从车道池移除并告警；
- 风控 strike 达到 3/4（`RISK_STRIKE_GUARD`）时，网关本身会暂停打上游，不要绕过。

### 7.3 时间/金额保险

- `data/burn/STOP` 文件：任何时刻 `touch` 即全停；
- 08:50 硬截止（脚本内置），无论剩多少都停；
- 剩余 ≤ 5M 时停（避免最后一点额度触发上游异常）；
- 每 15 分钟巡检工单核对：速率、剩余、错误率、各账号分布；异常自动降速/停机。

## 8. 续派工单改造（多炉位）

现状：钩子 v0.3.0 只有一个全局 `next-prompt.txt`，多会话会抢同一条指令。
要把“主炉 + 4 旁路”真正跑起来，需要把单炉位扩成多炉位。

### 8.1 文件协议（向后兼容）

```
continue.sessions 每行：
    sess_xxx                 → 默认 slot=main（老格式，兼容）
    sess_xxx|main            → 主炉
    sess_yyy|s1              → 旁路 1
    ...

data/_sup/
    next-prompt.main.txt     ← 主炉指令（不存在 = 主炉空闲）
    next-prompt.s1.txt       ← 旁路 1 指令
    ...
```

### 8.2 代码改动（约 30–45 分钟）

| 文件 | 改动 |
|---|---|
| `~/.zcode/cli/plugins/.../continue.mjs` | 解析 `session_id|slot`；按 slot 读 `next-prompt.<slot>.txt`；消费后归档为 `next-prompt.<slot>.used-*.txt` |
| `app/burner.py` | 工单加 `slot` 字段（默认 `main`）；`state.json` 按 slot 记录 `dispatchedId/baseline`；`tick` 按 slot 独立派单/验收 |
| `app/routes/admin_burner.py` | `enqueue` 接收 `slot`；`state` 返回 per-slot 视图；新增 `dispatch-now?slot=` |
| `frontend/admin/supervisor.html` | 队列按 slot 分 tab；每个 slot 显示在途/排队/已完成 |
| `tests/unit/test_burner.py` | 补 slot 隔离、slot 验收、老队列默认 main 的用例 |

### 8.3 保守方案（不改钩子）

如果 30 分钟内改不完，退回：

- **主炉**：1 个会话，消费全局 `next-prompt.txt`，跑 P0 实现单；
- **旁路**：4 个会话各自打开在完美世界项目，用一次性长指令启动（“按 S1 清单逐项执行，
  每完成一项写进度文件，直到 08:30”）；不加入 `continue.sessions`，靠单次长任务自驱；
- **放大层**：不受影响，独立进程。

这个方案少烧 3–4 路真活的量（约 150–250M），但放大层可以在 05:30 前补上，风险可控。

### 9.2 SQL（直接可跑）

```sql
-- 近 1 小时各账号烧量
SELECT account,
       SUM(input_tokens + output_tokens + cached_tokens) AS units,
       COUNT(*) AS calls
FROM requests
WHERE ts > strftime('%s','now') - 3600
GROUP BY account ORDER BY units DESC;

-- 近 10 分钟速率（M/h）
SELECT SUM(input_tokens + output_tokens + cached_tokens) * 6 / 1e6 AS m_per_h
FROM requests
WHERE ts > strftime('%s','now') - 600;
```

## 10. 应急预案

### A. 放大层被风控（3012 连续出现）

1. 立即 `touch data/burn/STOP`，全停；
2. 用单账号、单车道、69K 上下文发一次探测；
3. 若探测 200：降到 2 车道、200K chars、`max_tokens=8` 重启；
4. 若探测 3012：停止放大层，只保留真活层；把剩余额度打到完美世界验收/审计单上；
5. 记录事故时间、账号、请求形状，写入 `docs/development/burn-incident-20261103.md`。

### B. 上游 429/3009 频发

- 降车道到 2，`gap=1s`，重试 3 次；
- 若 10 分钟仍不恢复，切到“单账号单车道 + 真活层 5 路”，目标 150M/h；
- 剩余额度按 150M/h 重算 ETA，若 > 09:00，优先保证账号不被禁用，接受烧不完。

### C. 工单管线断了（监听名单空/钩子没加载）

- 检查 `continue.sessions` 是否有当前会话 id；
- 检查 `~/.zcode/cli/config.json` 的 `plugins.enabledPlugins["zcode-supervisor-continue@ai-local-plugins"]`；
- 看 `data/_sup/hook.log` 最后一次判定；
- 临时方案：手动把 `next-prompt.txt` 内容贴进主炉会话，继续推进。

### D. 账号提前耗尽/被封

- 耗尽：正常，移出池；
- 封禁：立即停该账号全部流量，保留证据；用剩余账号继续；
- 若只剩 2 个可用账号，放大层降到 2 车道，目标 150M/h，优先真活层。
